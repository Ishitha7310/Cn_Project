D1 showed that the system works. D2 shows that it **adapts** and measures **how much better** that is than a static setup.

## 1. Automatic link monitoring

**Problem in D1:** the controller could accept link-utilization values, but nothing measured them.

**Solution:** `monitor_poller.py` runs inside NetManager. Every `interval` seconds (default 2, the experiments use 1) it:

1. reads the transmit byte counters of both ends of every switch-to-switch link,
2. computes `utilization % = max(delta_tx_a, delta_tx_b) x 8 / (delta_t x link_bandwidth) x 100` (capped at 100),
3. sends `{"type": "cmd", "action": "set_utilization", "switch1": 3, "switch2": 1, "utilization": 42.0}` to the controller on port 9000.

What the controller already did with that value:

* `monitor.py` smooths it (EWMA, alpha 0.5) and stores it for both directions of the link.
* `path_engine.py` recomputes routes when any link changed by 20 points or more since the last computation.
* Link cost for routing is `delay + 0.1 x utilization`, so a busy link becomes less attractive.
* The `smart` policy adds the bottleneck utilization of the path to its server score.

Start it with `nm> monitor on [--interval 1]`; `monitor status` shows the latest value per link. The dashboard shows the same values as bars.

**Why interface counters and not OpenFlow port statistics:** both read the same Open vSwitch port counters. NetManager already owns the links and runs as root beside Open vSwitch, so reading the counters there needs no change to the Ryu apps and cannot break forwarding. The price is that the measurement lives next to the simulator rather than inside the controller; on a real network it would be an OpenFlow `PortStatsRequest`.

## 2. Server selection policies

| Policy | Rule |
|---|---|
| `static` | First ACTIVE server. This is the baseline: no intelligence. |
| `round_robin` | Rotate over ACTIVE servers. |
| `least_conn` | ACTIVE server with the fewest active connections. |
| `smart` | Lowest score: `load / max_load + bottleneck_utilization / 100 + path_delay / 10` over the path from the client's switch to the server's switch. Only ACTIVE servers are considered. If it cannot decide (unknown client), the controller falls back to `least_conn`. |

Change at runtime: `python3 controller/ctl.py policy smart`.

`tests/test_d2.py` checks the behaviour: with the links behind `srv1` saturated, `smart` stops choosing `srv1` while `static` keeps choosing it; a heavily loaded server and a DOWN server are avoided.

## 3. Evaluation method

Run: `./run.sh experiments` (full, about 15-25 minutes) or `./run.sh experiments --quick` (about 5 minutes, to check your setup).

**Topology.** Leaf-spine with 2 spines. `S` server leaves (one server each), **one client leaf with no server**, and one extra leaf holding a traffic sink. Every switch link is 20 Mbps. Because the clients sit on a leaf with no server, every request crosses the spine, so both server choice and link load matter. (With a client on every server's leaf, `smart` always picks the local server and never touches the spine, which hides the effect we want to measure.)

**Workload.** Every client host runs `app/workload.py` concurrently: 2 workers x 2 downloads of `medium.bin` and `large.bin` (so 6 simultaneous flows from 3 hosts). Each download is recorded with response time, throughput, serving server, retries and status.

**Conditions**

| Condition | What happens |
|---|---|
| `normal` | No extra load. |
| `congestion` | 18 Mbps of UDP background traffic from the server the baseline uses, towards the sink. The links near that server are nearly full. |
| `failure` | That same server is killed 4 s into the run and restarted afterwards. Clients must reconnect and resume. |

**Design choices that matter for fairness**

* The same target server is used for every policy.
* Each repetition runs every policy in a random order, to avoid drift (VM load, warm caches) favouring one policy.
* The mean and standard deviation are taken over repetitions (3 by default), not over requests.
* Response time and throughput use successful requests only; the success rate is reported separately.

**Metrics:** mean response time (lower is better), p95 response time, mean throughput (higher is better), success rate, retries per request, and the share of requests each server served (load balance).

## 5. Live D2 demo (about 4 minutes)

Terminal 1: `./run.sh controller`. Terminal 4: `python3 ui/dashboard.py` (open http://localhost:8080). Terminal 2: `./run.sh net`, then at `nm>`:

```
gen_topo leaf-spine --spines 2 --leaves 5 --servers 3 --clients 0
add_clients 3 --on s6
add_host noisesink --on s7
wait_ready
announce_all
monitor on --interval 1
```

Then, typing one line at a time (no arrow keys):

1. `c1 python3 app/client.py --file large.bin` (baseline speed, note the server and Mbps)
2. In a normal terminal: `python3 controller/ctl.py policy static`
3. `iperf_noise srv1 noisesink --secs 60 --mbps 18` (use the server named in step 1 if it is not srv1), then watch the dashboard: link utilization bars rise on the links around srv1.
4. `c1 python3 app/client.py --file large.bin` with `static`: slower, still served by srv1.
5. `python3 controller/ctl.py policy smart`, then `c1 python3 app/client.py --file large.bin` again: it should be served by a different server and be faster. Check this on your VM before the demo; if the effect is small, use a longer noise duration or `--mbps 19`.
6. `kill_server srv2` during a download to show failure recovery, as in D1.

## 6. Limitations (say these before you are asked)

* **Simulation scale.** Mininet on one VM with 20 Mbps links; absolute numbers depend on the VM. Compare policies with each other, not with a real network.
* **Symmetric utilization.** The controller keeps one utilization value per link, not one per direction. Background traffic in one direction therefore also makes the other direction look busy.
* **Measurement interval.** Utilization is sampled every 1-2 s and smoothed, so very short bursts are not seen.
* **Scenario design.** The congestion and failure scenarios target the server the static baseline uses. That is the worst case for the baseline by design, so the size of the improvement is specific to this scenario.
* **Small workload.** 6 concurrent flows and a few downloads per run. More repetitions give tighter error bars.
* **Server selection happens per connection.** An established download is not moved to another server; only routing changes under it (link failure) or the client reconnects (server failure).

## 7. Likely viva questions

* **How is link utilization measured?** Transmit byte counters of both ends of each switch link every 1-2 s; the busier direction divided by the link bandwidth.
* **What does the controller do with it?** Smooths it (EWMA), recomputes routes when a link changes by 20 points, uses it in link cost and in the `smart` score.
* **How does `smart` choose?** Lowest of normalised server load + bottleneck link utilization on the path + path delay.
* **What is your baseline and why?** `static`, always the first ACTIVE server: what you get without any intelligence in the network.
* **Why are clients on a separate leaf?** So every request crosses the spine; otherwise `smart` picks the local server and link load never matters.
* **What happens when the chosen server dies mid-download?** Heartbeats stop, the controller marks it DOWN after 3 s, the client reconnects to the virtual IP and resumes from the byte offset it already has.
* **What happens when a link dies?** The controller recomputes paths and rewrites only the changed routing rules; the virtual-IP rewrite on the edge switch is untouched, so the TCP connection survives.
* **What are the weaknesses of your evaluation?** See section 6.
